# 模板编辑页：内联预览 + 视口切换 设计方案

> 范围：`ui/src/views/template/edit.vue` 主编辑区（非 AI 抽屉路径）
> 状态：**设计稿，未动任何源码**。实现前需与作者确认方案选型。
> 关联文件：`edit.vue`、`composables/useAiPreview.ts`、`composables/usePreviewIframeHooks.ts`、
> `starters/ai-starter/.../AiTemplatePreviewController.java`

---

## 0. 先说结论（基于已核实的代码事实）

两个问题的根因**都在前端**，后端能力已经齐备：

1. **内联预览的后端能力已存在，且 AI 与手动走的是同一套管线。**
   `AiTemplatePreviewController`（`starters/ai-starter/.../AiTemplatePreviewController.java`）
   的两个入口：
   - `/ai/template/preview/{sessionId}/{templateName}/**`（AI 会话，:69）
   - `/template/preview/{templateId}/**`（正式模板，:113）

   都汇入**同一个** `servePreview()`（:157），其分发逻辑（:171-175）：
   - `.html` → `renderTemplate()`（:185）：**FreeMarker mock 渲染**，每次重新加载
     `_preview_data.json`，`ctx()` 会把静态资源基路径改写到本预览前缀下；
   - 其余（**css / js / 图片 / 字体**等）→ `serveStaticFile()`（:202）：
     `MediaTypeFactory.getMediaType(文件名)` 定 Content-Type + `Files.copy` 原样输出。

   也就是说：**预览后端不只是返回 HTML，CSS/JS/图片/字体全部能按相对路径正确加载，
   且模板里的 mock 数据（`_preview_data.json`）实时生效。** 手动路径和 AI 路径吃的是
   完全相同的资源管线 → 内联预览"渲染出完整带样式的页面"这条假设成立。

2. **前端 `useAiPreview.ts` 也早就同时拼好了两条 URL。**
   `useAiPreview.ts:59-68`：
   - 会话视图 → `/ai/template/preview/{sessionId}/{templateName}/{entry}`
   - **非会话视图 → `/template/preview/{templateId}/{entry}`**（line 65-67）

   连"新窗口打开"都复用它（`openInNewWindow`，line 107-109，用的就是 `aiPreviewUrl`）。
   所以**拼 URL、iframe、刷新键、页面下拉、空态占位这些积木全都有了**，只是
   `edit.vue:109` 把整个预览列用 `v-if="state.aiMode === 'adjust' || state.sessionView"`
   锁死在 AI 抽屉里，手动编辑区（`edit.vue:84-96` 的 `:sm="19"` 列）里**根本没有渲染这个 iframe**。

**因此 #1 不是"要不要做预览能力"，而是"把已有的预览列搬到/复用进主编辑区"。**
#2（视口切换）则是真正要新加的一块 UI，但目前预览框架（`.preview-toolbar` + `.preview-frame-wrap`）
留了很干净的扩展位。

## 1. 问题一：主编辑区内联预览（消除"割裂"）

### 1.1 现状（割裂的两套体验）

| 路径 | 触发 | 预览形态 | 代码位置 |
|------|------|----------|----------|
| AI 调整 / 会话编辑 | 点「AI 调整」进抽屉 | **左 iframe 内联预览 + 右对话**，AI 每写一个文件自动刷新 | `edit.vue:109-130` |
| 手动改代码 | 直接编辑 + 点「预览」 | **`window.open` 新标签页**，编辑区无预览 | `edit.vue:28` → `onPreview`（line 386-407，`window.open('/template/preview/...')`） |

同在一个页面，"改代码"和"AI 改"两条路的预览体验完全不同：一个有内联、一个只能跳走。
割裂点就是 `edit.vue:109` 的 `v-if` 条件 + `onPreview` 里独立的 `window.open`。

### 1.2 目标

手动编辑时也获得和 AI 一致的内联预览：**改代码 → 右侧（或旁边）实时看到渲染效果**，
并保留"新窗口打开"作为兜底/放大查看。让"内联预览"成为主编辑区的常驻能力，
AI 抽屉只是在这个能力之上再叠加了对话。

### 1.3 布局方案（3 选 1，推荐 A）

当前主编辑区是 `el-row` 两列：`:sm="5"`（文件树）+ `:sm="19"`（CodeMirror/图片工作台）。

**方案 A：三列常驻（文件树 | 代码 | 预览）—— 推荐**
- 把预览列从抽屉里"提出来"，作为主编辑区第三列。
- 列宽：`文件树 :sm="4" | 代码 :sm="8" | 预览 :sm="12"`（可按比例微调）。
- 预览列复用**现有** `.preview-toolbar`（页面下拉 + 刷新 + 新窗口）+ `.preview-frame-wrap`（iframe）。
- 直接消费 `useAiPreview` 已经算好的 `aiPreviewUrl` / `previewPageOptions` / `preview.entry`，
  因为非会话视图下它拼的正是 `/template/preview/{templateId}/{entry}`。
- **优点**：和 AI 路径**同一套 DOM 结构、同一套样式**，真正做到"不割裂"；改动集中在
  `edit.vue` 模板部分（新增一个 `<el-col>`），逻辑几乎零新增。
- **代价**：屏幕被分三份，CodeMirror 变窄；窄屏（< 1200px）体验需处理（见 1.5 响应式）。

**方案 B：代码/预览叠放（tab 切换）—— 改动最小但体验倒退**
- 在现有 `:sm="19"` 列里，用「编辑 / 预览」两个 tab 切换 CodeMirror 与 iframe。
- **优点**：不动列布局，改动最小。
- **缺点**：违背"改代码同时看效果"的核心诉求——切到预览就看不到代码了，
  反而比现在的 `window.open` 更别扭。**不推荐。**

**方案 C：预览默认收起、按需展开（split-view 开关）—— 兼顾但多一个开关**
- 在方案 A 基础上，预览列默认 `v-show=false`，工具栏加一个「预览」开关（或复用现有
  「预览」按钮改为 toggle 内联预览）。
- **优点**：屏幕小的用户不强制三列。
- **缺点**：比方案 A 多一个状态 + 多一次交互；和你"能省则省、别加开关门控界面"的偏好相悖
  （你曾否决 `design.enabled` 门控、要求"选项永远显示"）。
- 结论：如果接受"预览永远可见"，**直接用方案 A**；只有当三列确实挤时才退到 C。

> 按你一贯的极简偏好：**默认走方案 A（预览常驻可见，不门控）**。
> 若你担心小屏拥挤，再告诉我，我退 C。

### 1.4 关键实现点（方案 A）

1. **预览列模板**：把 `edit.vue:109-130` 的 `ai-preview-col` 内容抽成一个可复用片段
   （或直接内联到主编辑区新列）。建议抽成一个 `TemplatePreviewPanel.vue` 组件
   （或 `previewColumn` 内联块），入参 `:preview-url` `:page-options` `v-model:entry`
   `@refresh` `@open-new-window`，主编辑区和 AI 抽屉**共用它** → 彻底消除两套 DOM。
   > 这步是"去重"：现在 AI 抽屉和主编辑区若各写一份预览列，等于复制了 `preview-toolbar`
   > 和 `preview-frame-wrap` 两块样式。抽组件后两处都 `<TemplatePreviewPanel .../>`。

2. **数据源已就绪**：`useAiPreview` 已返回 `aiPreviewUrl`、`previewPageOptions`、
   `preview.entry`、`refresh`、`openInNewWindow`、`initEntry`。主编辑区直接复用，
   **无需新拼 URL、无需新请求**。`initEntry()` 在非会话视图下已按"当前编辑的可路由 HTML
   → index.html → 第一个页面"的顺序选入口（`useAiPreview.ts:88-99`），行为正确。

3. **手动编辑的刷新时机**：AI 路径靠"AI 写盘"触发 `preview.key = Date.now()` 重载。
   手动路径没有"AI 写盘"事件，需明确刷新策略（二选一）：
   - **(推荐) 保存后刷新**：`onSaveFile` 成功后调 `refresh()`。语义最干净——
     预览的永远是**已保存**内容，和 `serveTemplateFile` 读磁盘一致，不会出现"改了没存、
     预览却是旧的"的误导。代价：预览不随敲键盘实时更新，但模板编辑本来就是"存一次看一次"，
     可接受，且和现有 dirty 提示（`edit.vue:40` `● 有未保存的修改`）逻辑自洽。
   - **防抖实时刷新**：`onChange` 后 debounce（如 800ms）再 `refresh()`。体验更"活"，
     但预览的是**未保存**内容，与后端"存盘才生效"不符，且频繁 reload iframe 有性能与
     未保存内容泄露到预览的副作用。**除非你明确要"敲代码即见"，否则不推荐。**
   - 保留「刷新」按钮（`refreshAiPreview`）作为手动兜底，不变。

4. **`onPreview`（新窗口）去重**：`onPreview`（`edit.vue:386-407`）现在是独立拼
   `window.open`。方案 A 下"新窗口打开"已由预览列里的 `openInNewWindow` 提供
   （`useAiPreview.ts:107-109`，且它拼的是带 `?t=key` 的完整 URL，比 `onPreview` 里那个
   不带时间戳的更不容易吃缓存）。
   建议：**主编辑区删掉独立的「预览」按钮**（`edit.vue:28`），新窗口能力并入预览列工具栏，
   避免"预览"一个词在页面上指两个动作（一个内联一个新窗口）的歧义。
   > 若你想保留工具栏顶部那个「预览」按钮，就把它改成"聚焦/展开预览列"，不要再 `window.open`。

5. **点选换图 / 选区钩子的归属**：`usePreviewIframeHooks`（`onPreviewFrameLoad` 等）
   目前只服务于 AI 抽屉的 iframe（换图模式、选区模式、链接拦截）。主编辑区新增的
   预览 iframe **是否需要**这些钩子？
   - 换图/选区是 **AI 调整专属**（配合右侧 AI 对话），手动编辑区没有对话列，
     这些按钮没有落点 → **主编辑区预览列不接这些钩子**，只保留"渲染 + 刷新 + 新窗口"。
   - 实现上给 `TemplatePreviewPanel` 一个 `:with-pick-hooks` 开关：AI 抽屉传 `true`，
     主编辑区传 `false`。这是**组件内可选行为**，不是"后端配置门控界面"，不违背你的偏好。

### 1.5 响应式（窄屏）

三列在 < 1200px 会挤。最小处理（不引入新库）：
- 用 `el-col` 的断点：宽屏三列；`< 1200px` 时把预览列 `v-show` 掉、或在工具栏给个「预览」
  toggle（这是**布局适配**，不是功能门控，可接受）。
- 或更简：预览列 `min-width: 360px`，窄屏时横向滚动。**不推荐**（体验差）。
- 建议默认三列，窄屏时预览列 `el-col` 断点收为"抽屉式浮层"或隐藏——具体阈值实现时定，
  设计稿先定"宽屏三列常驻"为主目标。

## 2. 问题二：预览视口 / 设备切换（移动端验证）

### 2.1 现状

grep 确认整个 `template` 目录**无任何** `viewport` / `device` / `375` / 响应式切换逻辑。
但 `CreateTemplateDialog.vue:54-56` 里 `mobileAdaptive` 是**一等公民选项**（默认开，
生成"多端断点 + 汉堡菜单"）。矛盾点：

> 我们让用户（或 AI）生成响应式多端模板，却**没有任何办法在预览里切到手机宽度验证效果**。
> 用户只能 `window.open` 后用 F12 设备模拟去看——完全脱离编辑上下文。

### 2.2 目标

在预览 iframe 上提供**视口宽度切换**，让桌面 / 平板 / 手机宽度一键切换，
直接在编辑上下文里验证响应式断点（断点折叠、汉堡菜单出现、栅格重排）。

### 2.3 设计（一个下拉，不堆重 UI）

在 `preview-toolbar`（现有 `edit.vue:110-121`）里，**页面下拉**旁边加**一个**
视口下拉（`el-select`），选项三档：

| 选项 | 宽度 | 说明 |
|------|------|------|
| 桌面 | 100%（撑满预览列） | 默认 |
| 平板 | 768px | 居中，两侧留灰底 |
| 手机 | 375px | 居中，两侧留灰底（iPhone 宽度档） |

- 选中非 100% 时：iframe 容器 `.preview-frame-wrap` 内加一个**居中 wrapper**，
  给 iframe 设 `width: {px}; margin: 0 auto;`，两侧用 `.preview-frame-wrap` 的
  灰底（`var(--el-fill-color-light)`）衬托，模拟真机居中。
- 加 `?t=key` 不变；视口切换只改 iframe 的 CSS 宽度，**不重载 iframe**（纯样式，零请求）。
- 视口状态可存 `preview.viewport`（`useAiPreview` 的 reactive 里加一个字段），
  切换时不 bump `preview.key`（避免无谓重载）。

> **只加一个下拉**，不引入"自定义宽度输入框 / 设备列表 / 旋转开关"等重设计。
> 如果后续真要"任意宽度"，再加一个"自定义"项 + 数字输入——但那是二期，现在三档够用。

### 2.4 实现点

1. `useAiPreview.ts`：`preview` reactive 加 `viewport: 'desktop' | 'tablet' | 'mobile'`
   （默认 `'desktop'`）；导出 `viewportWidth` computed（`100% / 768px / 375px`）。
   - 不 bump `key`，切换即时生效。
2. `edit.vue` / `TemplatePreviewPanel`：
   - `preview-toolbar` 加一个 `el-select` 绑 `preview.viewport`。
   - `.preview-frame-wrap` 结构改为：
     ```
     .preview-frame-wrap
       └─ .preview-viewport-stage (灰底, 居中容器, overflow auto)
            └─ iframe.preview-frame (width = viewportWidth)
     ```
   - CSS：`.preview-viewport-stage { flex:1; min-height:0; overflow:auto;
     background: var(--el-fill-color-light); display:flex; justify-content:center; }`
     `.preview-frame { height:100%; background:#fff; }`（宽度由内联 `:style` 注入）。
   - 桌面档（100%）时 iframe `width:100%`，灰底自然不可见（铺满），视觉与现在一致
     → **不影响现有桌面预览观感**。
3. 复用性：`TemplatePreviewPanel` 组件直接带这个视口下拉（AI 抽屉和主编辑区都能用，
   AI 调整时同样能切手机宽度看——顺带修了"AI 生成响应式但抽屉里也没法切手机验证"的同类问题）。

### 2.5 不做的事（保持极简）

- 不引入 `@vueuse` 的设备模拟、不引 Playwright/Puppeteer 截图。
- 不做"实时渲染截图预览"（那要 headless 浏览器，重）。
- 不做断点高亮/断点列表（IDE 级功能，超出"一键验证"诉求）。

## 3. 两个问题合起来的落地顺序（若你批准）

1. **抽 `TemplatePreviewPanel.vue`**（页面下拉 + 刷新 + 新窗口 + 视口下拉 + iframe），
   AI 抽屉和主编辑区共用 → 一步同时解决"去重"和"复用"。
2. **主编辑区加第三列**（方案 A），挂 `<TemplatePreviewPanel>`，数据源用现有 `useAiPreview`。

4. **视口下拉**：`useAiPreview` 加 `viewport` 字段 + `TemplatePreviewPanel` 加 `el-select`
   与 stage 容器 CSS。
5. 窄屏适配（`el-col` 断点 / 预览列收起）。

> 每步都是**前端局部改动**，不动后端、不动 API、不引新依赖、不加配置开关。
> 后端 `/template/preview/{templateId}/**` 已能服务全套资源，**无需任何后端改动**。

# 附录：AI 操作独立化 —— 「AI 工作台」设计方案

> 本节是上一稿（内联预览 + 视口切换）之后的独立化延伸，对应交互稿
> `交互设计稿-模板编辑-AI工作台.html`。核心：把 AI 从「手动编辑器工具栏里两个橙色按钮 + 一个吞全屏的抽屉」
> 升级为与「手动编辑」平级的一级视图，AI 不再和手动编辑器抢同一块屏。

## 一、为什么独立（根因）

现状问题不是 AI 功能少，而是**它寄生在手动编辑器里**：

- 工具栏 `edit.vue:31-36`：「✦ AI 调整」「✦ AI 新建模板」两个橙色按钮和 上传/预览/保存/删除 平铺，AI 与文件操作无分组视觉分隔。
- 点开任一 AI 按钮 → `el-drawer size="100%"`（`edit.vue:102`），**全屏吞掉整个手动编辑器**，用户失去文件树/代码的视线，手动编辑这条线被 AI 完全接管。
- 两个按钮实际是同一个抽屉的两个入口，复用同一个 `aiChat.vue`，只靠 `aiMode` 区分文案——用户感知不到「调整」和「新建」是两个不同性质的操作。

**数据模型其实天然分两类**（这是独立化的依据）：

| 会话类型 | 后端标志 | 行为 | 预览指向 |
|---|---|---|---|
| 调整型 adjust | 绑 `templateId`（`edit.vue:425`） | AI 输出**直写正式模板目录**（后端自动备份），支持按轮回滚 | 正式模板 `/template/preview/{templateId}/**` |
| 生成型 generate | 无 `templateId`（`edit.vue:466`） | 在**会话工作目录**生成完整模板，「应用模板」后才复制到正式目录 | 会话目录 `/ai/template/preview/{sessionId}/**` |

既然两类会话本就分离，UI 就该把它们摆在「AI」这个独立工作区里，而不是塞进手动编辑器的抽屉。

## 二、方案：AI 工作台 = 与手动编辑平级的一级视图

**导航层级**（最小改动，不碰后端路由，复用前端 tab / 视图切换）：

```
模板
 ├─ 手动编辑   ← 现有 edit.vue（三列：文件树 | 代码 | 内联预览+视口）
 └─ AI 工作台  ← 新增 aiWorkbench.vue（三列：AI 会话 | AI 对话 | 内联预览）
```

- **手动编辑器**：删掉「✦ AI 调整」「✦ AI 新建模板」两个橙色按钮，收敛成一个「✦ AI 工作台」入口（或顶部 tab 直接切过去）。手动编辑从此只服务手动编辑。
- **AI 工作台**：承载全部 AI 能力（调整 / 新建 / 历史会话 / 设计稿确认 / 应用模板），AI 对话与预览各得其所，不再吞全屏。

> 视图切换用 el-tabs 或顶部 segment 即可，**不新增后端路由**、不新增页面文件层级——这是「最简、别搞重设计」的边界：AI 工作台是一个新 view 组件，但它是「视图」不是「新菜单/新路由」。

## 三、AI 工作台布局（三列）

```
┌─────────────────────────────────────────────────────────────────────┐
│ 模板 ▾    [ 手动编辑 | AI 工作台 ]          ● 状态                     │
├──────────────┬──────────────────────────────────┬───────────────────┤
│  AI 会话      │  AI 对话                          │  内联预览          │
│              │                                  │  [视口: 桌面▾]     │
│ [调整]       │  ┌ 会话: 调整 #20260916-14      ┐ │                   │
│  · 首页配色   │  │ 用户: 把导航改成深色…        │ │   ┌─────────────┐ │
│  · 换 hero 图 │  │ AI:  已修改 _layout.html…   │ │   │  响应式网站   │ │
│ [生成]       │  │ 用户: 再调一下标题字号        │ │   │  (adjust:正式│ │
│  · 企业官网   │  │ AI:  已修改 index.html      │ │   │  generate:工作│ │
│  · 电商模板   │  └──────────────────────────┘ │   │  目录)        │ │
│              │  ┌ 本轮修改文件 (2)             ┐ │   └─────────────┘ │
│              │  │ ▸ _layout.html  [回滚]      │ │  ● 已保存/生成中    │
│              │  │ ▸ index.html    [回滚]      │ │                   │
│              │  └──────────────────────────┘ │                     │
│              │  ┌ 输入：描述你要调整的内容…   ┐ │                     │
│              │  │                    [发送]  │ │                     │
│              │  └──────────────────────────┘ │                     │
└──────────────┴──────────────────────────────────┴───────────────────┘
```

**三列分工**：

1. **AI 会话列**（左，窄）：按 `调整 / 生成` 分组的会话列表，复用现有 `aiChat.vue` 顶部会话下拉（`aiChat.vue:8`）的数据源 `aiSessions`。
   - 调整组：每个绑定当前模板的 adjust 会话（可切换/续聊）。
   - 生成组：每个 generate 会话（未应用=可继续对话打磨；已应用=只读回看，`aiChat.vue:25` 的 `已应用（仅回看）` 标签）。
   - 顶部两个动作：**＋ 调整当前模板**（= 现 `onOpenAiAdjust`）、**✦ 新建模板**（= 现 `onOpenAiCreate`，仍先弹 `CreateTemplateDialog` 收集需求）。

2. **AI 对话列**（中，主）：直接复用 `aiChat.vue`（消息流 / token / 设计稿确认卡 / 输入框按 mode 换文案 / 发送·停止 / 本轮修改文件 / 回滚 / 应用模板）。**不重写对话面板**，只把它从抽屉里「解放」成工作台的主列。
   - adjust：输入框 placeholder「描述你想调整的内容，例如：把首页导航改为深色」（`aiChat.vue:156`）。
   - generate：「生成一个企业官网模板，蓝色调，响应式设计」。

3. **内联预览列**（右）：复用上一稿的 `TemplatePreviewPanel`（视口切换 + 保存/生成后刷新 + 演示站点）。
   - adjust 模式 → 预览正式模板 `/template/preview/{templateId}/**`，AI 每轮直写后刷新，用户看着正式模板实时变。
   - generate 模式 → 预览会话工作目录 `/ai/template/preview/{sessionId}/**`，AI 每写完一个文件刷新（`onCreateDialogCreated` 的现有行为）。
   - 点选换图/选区钩子在这里**接通**（AI 对话专属，`aiChat.vue:197` 的「点选工具」），这是工作台比抽屉强的地方：对话和预览并排，点选→发送→看效果一气呵成。

## 五、待拍板决策点

| # | 决策 | 推荐 |
|---|---|---|
| 1 | 「AI 工作台」是 el-tabs 视图 还是 独立顶级菜单项？ | **el-tabs 视图**（手动编辑 / AI 工作台 两个 tab），不碰后端路由 |
| 2 | 手动编辑器还保留 AI 入口按钮吗？ | 删掉两个橙色按钮，改在工具栏放一个「✦ AI 工作台」跳转（或直接靠 tab） |
| 3 | AI 工作台预览是否接通点选换图/选区钩子？ | **接通**（对话+预览并排，体验闭环；这是脱离抽屉的最大收益） |
| 4 | 生成型会话「应用模板」后是否自动跳回手动编辑 tab？ | 应用后弹 toast + 给「查看正式模板」按钮（跳到手动编辑并加载该模板），不强制跳转 |
| 5 | 会话列表分组（调整/生成）是固定两段 还是 单列表带类型 tag？ | **固定两段**（调整在上、生成在下），符合「AI 操作独立分开」的诉求 |
